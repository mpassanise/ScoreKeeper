# Atomic local game queue — Phase 3, increment 4

Status: inactive repository foundation for both web IndexedDB and iPhone SQLite. Neither live scoring writer calls it. No HTTP sender, background task, optimistic account UI, guest adoption or automatic retry loop is installed. All existing pilot flags and `ScorekeeperGameOperationsEnabled` stay false.

## Atomic storage and identity

`createDurableAccountRepository(...).outbox(lease)` exposes a guarded queue. A single versioned metadata document per profile holds confirmed bases, immutable request strings, optimistic projections and delivery receipts. Updating the operation and its projection is one document CAS transaction. This uses existing database schema 2; no IndexedDB/SQLite schema upgrade or Azure migration is required. Confirmed snapshot records and legacy local game sources are never overwritten by enqueue or acknowledgement.

`AtomicDocuments.write` now accepts revision guards. IndexedDB checks them in the same strict-durability transaction that writes the document; SQLite checks them in the same exclusive transaction. Queue writes guard the account lifecycle revision as well as the outbox revision. A sign-out, account switch, re-verification or deletion from another handle cannot slip between a lifecycle read and the queue commit. A write ordered before sign-out can legitimately commit; the subsequent lifecycle block prevents access/delivery. CAS/contention errors preserve the original request for explicit retry; they never generate replacement IDs.

The account guard supplies the profile ID, never an email, UI-provided owner or token. Pending/forged/stale/deleting leases fail closed. A current server-verified lease grants local queue writes for that process even after connection loss; connection loss revokes delivery permission. Restoring a retained session after process restart permits read-only pending recovery, matching the existing privacy policy, but requires fresh verification before queue writes or delivery. This conservative restored-session policy remains an activation decision: full cold-start offline scoring is not enabled by this increment. Sign-out and deletion block access without reclassifying queued data as guest games. Account deletion/local erasure acceptance remains a rollout gate.

## Queue behavior

- `seedConfirmed(gameId)` reads a complete confirmed snapshot through the guarded repository. It cannot adopt a caller-provided local game or replace an existing queued base. Creation/import are separate explicit envelopes; no adoption UI is installed.
- `enqueue(operation)` serializes and validates before its first await. Stable IDs, expected versions, explicit undo/score targets and scoring rules are preserved. The pending request string never changes. The queue derives the local projection using the shared scoring implementation and persists a stable local timestamp. Creation/import preserve player/history IDs; import starts the optimistic server version at 1. Deletion hides the local projection while retaining the base and pending deletion.
- Local retry of the identical ID/string is a no-op. A changed string under that ID is rejected. The inactive client validator intentionally accepts canonical lowercase GUIDs and JSON generated by serialization, rejects device/cache-only fields and duplicate/noncanonical JSON, and does not claim that its string equality is the server's typed fingerprint algorithm.
- Delivery is ordered per game. `prepareDelivery(gameId, capability)` requires fresh verification and a compatible advertised capability. Lifecycle operations require the corresponding `kinds` entry; actions require their advertised action. It commits `uncertain` before returning request bytes to a future transport. If process loss occurs before a sender actually transmits them, replaying that same operation is still safe.
- A timeout, transport error, token loss or missing capability does not delete/rebase a request or mark it rejected. After reconnection, `prepareDelivery` returns the same uncertain bytes. This layer has no network side effects itself; the future transport must recheck/abort on lifecycle changes and call the authenticated receipt endpoint with those bytes.
- `acknowledge(operationId, receipt)` validates IDs, outcome, versions and error codes. It only accepts the first dispatched unresolved operation, and commits the receipt atomically. A lost local response after acknowledgement can be retried idempotently. A rejected receipt blocks its dependants for review; original requests and projections remain available, without silent rollback, discard or version rebasing.
- Receipt metadata never creates a confirmed game snapshot. Even when every operation is applied, the optimistic projection is not server-confirmed content. Authoritative refresh/reconciliation and queue compaction are separate next steps; no old receipts/bases are removed here.

The document currently bounds each profile to 50 staged games, 500 retained operations and 8 MB, with a 2 MB maximum operation. Capacity errors stop new writes without eviction. These are conservative inactive pilot limits, not an app-wide game limit. No application-wide queue enumeration, cross-tab leader election, retry scheduling, garbage collection or public UI is added. Before activation, performance/compaction design must avoid an ever-growing document and excessive projection replay work.

Every read validates stored identity, operation/version order, receipts and the reconstructed projection. Unknown/corrupt versions or divergent projections are retained and reported as storage corruption; nothing is reset or replaced with an empty queue.

## Evidence and limits

`node scripts/test-game-outbox.mjs` runs the same production repository code against fake IndexedDB and real file-backed desktop SQLite. It covers atomic queue/projection writes, caller mutation, immutable-ID retries, local write/response failures, ordered delivery, network acknowledgement loss, acknowledgement write failure/retry, reopen recovery, capability/auth gates, terminal conflicts/dependants, lifecycle operations, targeted undo, stable entry-ID reuse rejection, total-mode semantics, concurrent CAS and lifecycle-revocation races, account isolation/deletion blocking, corruption preservation, and SQLite process death before/after commit. The network receipt server in this script is a test double; production SQL receipt correctness remains covered by the separate real SQL CI job.

Existing durable repository, lifecycle, staging and pilot regressions remain required, alongside API, web and mobile typecheck/export. Desktop SQLite and fake IndexedDB evidence does not replace browser quota/eviction checks, physical-iPhone bridge/OS durability, authentication/HTTP end-to-end tests or full account lifecycle acceptance.
